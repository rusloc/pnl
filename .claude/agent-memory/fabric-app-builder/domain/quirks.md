### QRK-001 · `connector inspect --name` does not interpolate `${VAR}` in `connectors[].config` · 2026-10-21
**What:** With `workspaceId: ${LH_RAW_WORKSPACE_ID}` in `rayfin.yml`, `npx rayfin connector inspect --name lhraw --entity acme_pl.dim_entity` fails `Fabric API error: 400 Bad Request`. Same command with literal IDs returns rows. `connector list --json` and `up --dry-run` DO resolve the placeholders.
**Why / Evidence:** Reproduced 2026-10-21 by swapping literals ↔ `${VAR}` in `rayfin.yml` and re-running; direct mode (`--workspace-id … --item-id … --type fabric-sqlanalytics --entity acme_pl.dim_entity`) works regardless.
**Workaround:** use direct mode for inspect; keep `${VAR}` in `rayfin.yml` for deploys.
**Scope (refined 2026-10-21):** `inspect --name` only. `connector invoke pnlModel executeQuery --file …` with `workspaceId: ${PNL_MODEL_WORKSPACE_ID}` / `itemId: ${PNL_MODEL_ITEM_ID}` in `rayfin.yml` and the values in `rayfin/.env` succeeded three times (ROW, INFO.VIEW.MEASURES, Q1) — ADR-0006 §3.20 answered: `invoke` interpolates, `inspect` does not. No Power BI consent prompt appeared for an identity that had already run `rayfin login`.
**Where:** `fabric-app/rayfin/rayfin.yml`, `fabric-app/rayfin/probes/*.query.json`
**Versions:** rayfin-core 1.36.2 · rayfin-cli 1.36.2

### QRK-003 · Connector entities support server-side `groupBy` / `aggregate` (DAB); the skill says nothing about it · 2026-10-21

The skill's `data-client.md` lists only `select/where/orderBy/first` and "no count()", and `connectors.md` shows only `select…first…execute`, so a reader of the skill alone would conclude the browser must page facts.
**Why / Evidence:** `node_modules/@microsoft/rayfin-connectors/dist/category-a/ConnectorEntityClient.d.ts` (methods `groupBy`, `aggregate`), `ConnectorsSchema.d.ts` (`read` ops include `"groupBy", "aggregate"`), `node_modules/@microsoft/rayfin-data/assets/docs/aggregations.md`; `rayfin-connector-fabric-graphql/assets/docs/querying.md` points to it. Compile-verified in `pnl-aggregate.prototype.ts`; **not yet executed against lh_raw** (connectors run only deployed).
**Where:** `fabric-app/packages/frontend/src/pnl/data/pnl-aggregate.prototype.ts`, ADR-0005
**Versions:** rayfin-connectors 1.36.2 · rayfin-data 1.36.2 · rayfin-cli 1.36.2

### QRK-004 · Every connector request shares rayfin-lib `ApiClient`'s 30 s default timeout; the browser client can raise it, the CLI cannot · 2026-10-22
**What:** `ApiClient` sets `defaultTimeout = config.timeout || 30000` and aborts each fetch at that limit ("Request timed out after 30000ms", category `network`, misleading hint "The request never reached the service"). The semantic-model connector's browser transport (`SemanticConnectorClient.standaloneTransport` → `apiClient.requestRaw`) and the CLI direct path (`connector invoke`) both run through it. `RayfinClientConfig extends ApiClientConfig`, so `new ConnectorsRayfinClient({ …, timeout: 120_000 })` lifts the limit in the app; `connector invoke` exposes no timeout option, so any DAX slower than ~27 s cannot be probed from the CLI (on 2026-10-22 the Q1 statement with default filters and every `dim_kpi` SUMMARIZECOLUMNS probe timed out there; the sliced Q1 came back in 26 s).
**Why / Evidence:** `node_modules/@microsoft/rayfin-lib/dist/ApiClient.js:183,445,703`, `ApiClient.d.ts:36` (`timeout?: number`), `rayfin-client/dist/client.d.ts:26`; probes `rayfin/.temp/{q2-*,t1-kpi-value-only,q1-time}.json` 2026-10-22 (all "timed out after 30000ms" at 33–34 s wall). ADR-0006 §3.16 had the deployed timeout as unknown — it is this one.
**Workaround:** app: `timeout: 120_000` in `packages/frontend/src/lib/rayfin-client.ts`; CLI: split probes into chunks that finish < 25 s, or trust the unit tests + deployed app for the slow shapes.
**Where:** `fabric-app/packages/frontend/src/lib/rayfin-client.ts`, `fabric-app/rayfin/probes/q2-kpi-smoke.query.json` (the shape that never finishes)
**Versions:** rayfin-lib 1.36.2 · rayfin-cli 1.36.2 · rayfin-connector-fabric-semanticmodel 1.36.2
**Hits:** 2 · **Confidence:** high · **Tags:** timeout, api-client, connector-invoke, semantic-model, n-01
**Last-verified:** 2026-10-28 (QV3 `KPI Info Sub` × 10 codes = 24.8 s wall through invoke, 5 s short of the cap; the app's 120 s config covers it) · 2026-10-22 (16:05: the full old-shape default Q1 timed out again at 30 s; captured as its `_lines` / `_leaves` halves instead — the split-under-25-s workaround holds) · **Related:** DEC-003, LSN-005, LSN-006, QRK-001

### QRK-007 · No standalone typegen on cli 1.36.2, but `validate-functions.mjs` mirrors the generator, so a hand-written `types.ts` passes when it matches the checker's spelling · 2026-10-23
**What:** Typegen runs only inside `rayfin dev` / `dev functions apply` (needs Azure Functions Core Tools; none installed here). The pack's `scripts/validate-functions.mjs` re-serialises every `udf.func()` handler with the same code as `rayfin-cli/dist/utils/functions-types-generator.js` and compares the printed text with `packages/functions/src/types.ts`, so a `types.ts` written by hand in the generator's exact header + `  name: {` / `    input: ...;` / `    output: ...;` / `  };` format is accepted, and the later real typegen should be a no-diff. Spelling rules learned the hard way: (a) unions print `null` **first** (`null | string`, `null | { ... }[]`); (b) an optional property serialises as `x?: T | undefined` - use `T | null` instead; (c) a type whose declarations all live in a declaration file (a built workspace package such as `@rayfin-app/shared/dist`) is kept **by name** (`ChatTurnOutput`), which `types.ts` cannot resolve - declare contract types in `packages/functions/src/*.ts` (expanded structurally) and import only *runtime* values from shared; aliases of string-literal unions resolve fine; (d) `ReadonlyArray<T>` -> `T[]`; (e) every handler parameter other than the `RayfinContext<...>`-annotated one becomes an input field, so `(ctx, turn: X)` -> `input: { turn: X }`. `secrets.generated.ts` has a fixed render too (`rayfin-cli/dist/utils/secrets-types-generator.js`: header, `declare module '@microsoft/fabric-user-data-functions' { interface RayfinSecretRegistry { NAME: string; } }`, names sorted) and lands under `services.functions.path`/src, so it can be pre-written from the `secrets:` list in `rayfin.yml`. Spec files (`*.spec.ts`) are ignored by the validator; exclude them in the functions `tsconfig.json` and run them with vitest from the functions package.
**Why / Evidence:** `node scripts/validate-functions.mjs` 2026-10-23: the first run failed only on `string | null` vs `null | string` and `...[] | null` vs `null | ...[]` (debug print of `serializedHandlerContract` vs the generated text); green after the swap. Generator source read for the header and the by-name rule (`symbol.declarations.every(d => d.getSourceFile().isDeclarationFile)`).
**Where:** `fabric-app/packages/functions/src/{types,chat-contract,secrets.generated}.ts`, `fabric-app/scripts/validate-functions.mjs`
**Versions:** rayfin-cli 1.36.2 · fabric-user-data-functions 1.36.2
**Hits:** 1 · **Confidence:** high (reproduced against the validator; the real typegen run is still pending) · **Tags:** functions, typegen, validator, contract, secrets, ai-chat
**Last-verified:** 2026-10-23 · **Related:** QRK-005, DEC-006
**Status:** active - confirm "no diff" after the USER's first `npm run dev` typegen; then a skill-patch candidate (functions section: "typegen needs Core Tools; the validator accepts a matching hand-written types.ts")
