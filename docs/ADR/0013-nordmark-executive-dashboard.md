## 1. Context

"Nordmark Retail" is a fictional multi-category reseller (142 stores in three formats — hyper, super, convenience — plus e-commerce and wholesale; 9 categories; ≈ 1,100 suppliers; ≈ 68 k active SKUs; Netherlands + Belgium; EUR). The spec describes a Monday-trading-meeting page: twelve tiles (sales, margin, stock, supply, profit), status On track / Watch / Off track from per-KPI tolerance rules, budget / last-year / last-week comparators on a 4-5-4 retail calendar, drill pages behind one click.

Prototype v5 fixes the landing page: a 56 px side bar (Filters menu, How to read, More KPIs, Notes), a header with period · comparator · region switchers, one status line with an **overall-status pulse dot** and the three counts, **3 hero cards** (Net sales · Total margin % · Weeks of cover), **3 medium** (Markdown · Availability · EBITDA flash) and **6 small** cards (LFL growth · Front gross margin · Sell-through · GMROI · Supplier OTIF · Channel mix); Watch / Off-track cards washed in their status colour, bottom-aligned 13-week bars with a dotted target, every explanation behind ⓘ / binoculars / How-to-read pop-ups; fold 761 px at 1440 × 810; filters conceal cards in place. The data frame is **retail Week 43 of FY2026 (19–25 Oct 2026)**, comparator Budget, with the story **7 on track · 3 watch · 2 off track** and **two provisional tiles** (Total margin %, EBITDA flash — accrual / flash until the month-end true-up on 10 Nov).

The USER decided on 2026-10-27 that the new showcases ship in **two flavours — a custom JS app and a Power BI report — with no Rayfin flavour**, and that both are **packed into `.sync/` and finalized / hosted from the vosk.dev repo**. That delivery path makes **portability** the governing constraint: nothing in either flavour may depend on a Fabric workspace, a cloud connection or a tenant at runtime. On 2026-10-28 the USER approved v5 as the design target, asked to **start building in parallel**, and fixed three more points: the data home is **local Parquet from a deterministic Python generator** (no `lh_raw`), the JS flavour is a **standalone Next.js app** (standalone apps per report for the `.sync/` hand-offs), and the pulse dot follows the **literal** v5 rule.

Naming: the USER calls the JS flavour "Track A" and the Power BI flavour "Track B" for the new showcases (design README, coms 2026-10-27). In this repo the folders stay `js-report/` and `pbi-report/`, whose CLAUDE.md names are Track C and Track B. This ADR says **JS flavour** and **PBI flavour** to avoid the collision (open question 1).

Ten decisions follow. (a), (b), (h) and (i) are USER decisions of 2026-10-27 / 28 and carry no default — only the reasoning and the rejected alternatives. The rest record a **default** and the alternatives; the USER may overturn any of them, and §5 lists the ones that need an answer before phase 1 starts.

## 2. Decisions

### (a) Two flavours: custom JS app + Power BI report; no Rayfin flavour — decided (USER 2026-10-27)

**Decision:** the Nordmark dashboard is built twice — a Power BI report (PBIP: TMDL model + PBIR page) and a standalone Next.js app (h) — from the same generated dataset, the same requirement note and the same design target, reconciled through shared control totals and a parity row set. The Fabric app (`fabric-app/`) is not extended.

**Why:** USER decision 2026-10-27 (ADR-0011 (d) confirmed). The Rayfin shell is tied to the P&L's Ledger design system and to a Fabric data item, which (b) rules out; two surfaces are enough to prove the design and the numbers.

**Alternative:** three flavours as for the P&L — rejected by the USER; the Rayfin route stays on file as a later option that would read the PBI flavour's model once it lives in a workspace (ADR-0006 pattern).

### (b) Portable by construction: no Fabric / workspace dependency at runtime; local Parquet is the data home — decided (USER 2026-10-28)

**Decision:** the generator writes CSV + one Parquet file per table to `data/nordmark_retail_dummy_data/parquet/`; **both flavours read that folder; no `lh_raw` dependency.** The PBI flavour imports the files through a `DataFolder` text parameter (`expressions.tmdl`) and per-table partitions `Parquet.Document(File.Contents(DataFolder & "\<table>.parquet"))` with explicit `Table.TransformColumnTypes` — the Trucks / Mirelo pattern (ADR-0011 (b)). The JS flavour's build step reads the same folder and writes pre-aggregated Parquet under its `public/data/` with a Zod-validated `manifest.json` (ADR-0002 §2.2 / ADR-0011 (c)); the browser loads static files, there is no server, no API, no auth. **The pack for the vosk.dev repo is therefore self-contained:** the PBIP folder + the Parquet folder + a README for the PBI flavour; the standalone app folder (h) with its built `public/data/` for the JS flavour; one `.sync/{date}-nordmark-handoff.md` with the index (CLAUDE.md › Cross-repo sync folder: source of truth stays in `pbi-report/` / `js-exec/` / `data/`, `.sync/` holds the copy). No workspace IDs, connections or tokens anywhere in the pack.

**Why:** the USER's delivery path (finalize / host from another repo) is the forcing function; a lakehouse schema would make the pack depend on a tenant and on ginee's load + refresh cycle before the first pixel, exactly what ADR-0011 (a) avoided. Parquet is typed, small and already what both flavours read.

**Later (not part of this build):** schema `nordmark_retail` in `lh_raw` via a `fabric-data/lh_raw/load_nordmark_retail.py` in the `load_acme_pl.py` pattern (ADR-0003); the PBI model then switches its partition sources from `DataFolder` to the `SqlEndpoint` / `Database` parameters only. Nothing in the report layer changes.

**Alternatives:** (1) lakehouse first — rejected (above). (2) CSV straight into Power Query — Parquet is typed and ≈ 5–10× smaller; the Trucks and Mirelo PBIPs prove the path. (3) Ship the JS flavour's data as JSON — the loader (`hyparquet`) and the build tooling already exist for Parquet; JSON would be larger and untyped.

### (c) Data generator: Python, deterministic, story-first (totals fixed, cells allocated)

**Default:** `data/nordmark_retail_dummy_data/` in the Mirelo layout — `generator/generate.py` (+ `requirements.txt` pinned to the same numpy 2.5.4 / pandas 2.3.3 / pyarrow 26.0.0 as Mirelo, venv gitignored), `dims/`, `facts/`, `params/`, `parquet/` (+ `manifest.json`), `checks/control_totals_eur.csv`, `checks/verify.py` (independent re-computation, exit 1 on any failure), `README.md` (columns, rules to apply in measures — the contract both flavours build against, as for Mirelo). **Seed 20261028**; the same seed gives byte-identical files; `--out <folder>` as in Mirelo.

**Calibration rule (the difference from Mirelo):** Mirelo is driver-first (latent drivers → Poisson draws → calibrated until the totals land). Nordmark is **story-first**: the ALL-scope weekly totals of every card input (gross sales, markdown, returns, COGS, back margin, stock, forecast COGS, availability counts, PO lines, OpEx by type, budget) are fixed per week from the story series, then **allocated** to store × category cells by stable shares plus seeded noise, with each week's rounding residual pushed to the largest cell (the DEC-002 / C-31 allocation rule). The v5 Week-43 values are then exact at display precision by construction, not by tuning.

**Why:** the dashboard's value is a readable Week-43 story (7 / 3 / 2, two provisional tiles, the twelve ⓘ worked examples quoting €61.4 m, 36.3 %, 11.4 wks, 9.8 %, 94.1 %, €15.3 m, +3.4 %, 30.1 %, 63.1 %, 2.7×, 95.4 %, 68.4 / 19.9 / 11.7). Fixing totals first makes the story a parameter table, not an emergent property, and keeps `verify.py` trivial.

**Alternatives:** (1) driver-first like Mirelo — more "organic" cells, but every story number becomes a calibration loop and the ⓘ examples drift; rejected. (2) Hand-written Week-43 rows only (no history) — the 13-week bars, LFL (LY week) and GMROI (R52W) need 95 weeks; rejected.

### (d) Data grain: **week × store × category** for the executive facts; day grain not generated

**Default:** facts at retail-week grain, keyed by `week_key` (FY-week, see (e)), `store_code` (142 stores + the online site + the wholesale desk as sites, each with `channel_code` STORE / ONLINE / WHOLESALE) and `category_code` (9), plus the dimensions below. The twelve cards need:

| Table | Grain (one row per …) | Columns (beyond keys) | Feeds |
|---|---|---|---|
| `dim_week` | retail week, FY2025 W1 … FY2026 W52 | `week_start`, `week_end`, `fy`, `quarter`, `period` (4-5-4), `week_of_period`, `week_of_fy`, `ly_week_key`, `lw_week_key`, `is_actual` (≤ W43 FY2026), `season_code` | every window; LY by key, never by date |
| `dim_date` | day (for the calendar only, 728 rows) | `week_key`, trading-day flag | header labels; no fact joins it |
| `dim_store` | site (142 stores + ONLINE + WHOLESALE) | `country` NL / BE, `format` hyper / super / convenience / online / wholesale, `channel_code`, `region`, `open_date`, `close_date` (3 closures in FY2026), `refit_date`, `cluster` | LFL set, region / format switcher, channel mix |
| `dim_category` | category (9) | `category_name`, `division`, `cover_target_wks`, `gmroi_target`, `sellthrough_target` | targets "by category" (spec #14, #16) |
| `dim_supplier` | supplier (≈ 1,100) | `supplier_group`, `country`, `primary_category_code`, `rebate_scheme` | back margin, OTIF |
| `dim_cost_type` | cost type (SHRINK, STORE_OPEX, CENTRAL_OPEX, FULFILMENT) | | EBITDA composition |
| `dim_kpi` | the 32 catalogue KPIs | `kpi_code`, `domain`, `is_landing` (12 ★), `size` hero / medium / small, `direction`, `format`, `cadence`, `owner`, `drill_page`, `group` B1–B4, `lever`, `horizon`, `statement`, `is_provisional`, `is_stock` | card metadata, More-KPIs drawer, Filters menu attributes |
| `fact_sales_week` | week × store × category | `gross_sales` (ticket, ex-VAT), `markdown_value` (permanent + promo), `returns`, `net_sales` (= gross − markdown − returns), `units`, `cogs_landed` (standard landed cost), `transactions`, `back_margin_alloc` (supplier accruals allocated by COGS share, residual to the largest cell — so region / format scopes reconcile) | Net sales, LFL, Front GM, Markdown, Back / Total margin by scope, Channel mix, GMROI numerator, sell-through units |
| `fact_budget_week` | week × store × category (FY2026 all 52 weeks) | `net_sales_bud`, `gross_sales_bud`, `markdown_bud`, `cogs_bud`, `back_margin_bud`, `lfl_growth_bud` | every "vs Budget" Δ; plan channel mix = budget net-sales shares |
| `fact_supplier_income_week` | week × supplier | `rebate_accrual`, `promo_funding`, `listing_fees`, `is_provisional` | Source of `back_margin_alloc` (Σ ALL reconciles); supplier drill later |
| `fact_inventory_week` | week-end × location (142 stores + 2 DCs) × category | `on_hand_units`, `on_hand_cost`, `on_order_cost`, `in_transit_cost`, `aged_90_cost` | Weeks of cover, GMROI denominator (average on-hand cost over the 52 week-ends), aged stock (bench) |
| `fact_forecast_week` | week × category | `forecast_cogs` (forward weekly COGS) | Weeks of cover denominator (fallback R4W average COGS in both flavours) |
| `fact_availability_week` | week × store × category | `ranged_sku_days`, `in_stock_sku_days` (top-500 sellers, sales-weighted, pre-weighted counts) | Availability % |
| `fact_receipts_week` | week × store × category | `receipt_units` | Sell-through denominator (opening season stock + receipts) |
| `fact_po_week` | week × supplier | `po_lines_due`, `po_lines_otif` | Supplier OTIF % |
| `fact_opex_week` | week × cost_type × store-or-central × scenario ACT / BUD | `amount` | EBITDA flash (Total margin − shrink − store OpEx − central OpEx − fulfilment), its budget |
| `param_status_rule` | KPI × band | `watch_from`, `off_from`, `direction`, `basis` (budget / target / band) | the twelve status rules of v5 (one table, both flavours) |
| `param_target` | KPI × (category or ALL) | `target_value` | availability 97 %, OTIF 95 %, GMROI 2.5× (and per category), cover 9.5 wks (cost-weighted over categories), sell-through 62 % (season) |

Size: ≈ 95 weeks × 144 sites × 9 categories ≈ 123 k rows for `fact_sales_week`, the same order for inventory and budget, ≈ 100 k each for the two supplier facts; ≈ 0.6 M rows in total, Parquet in the low tens of MB, PBI Import refresh well under the P&L's 28 s baseline, and a JS pack of a few hundred kB after the build-time cube (week × country × format × channel × category × is_lfl; stores never ship until a drill page exists).

**No SKU dimension** in this build: the spec keeps SKU grain behind a click in the domain models; v5's drill button shows the drill *path* only. Availability ships as pre-weighted SKU-store-day counts (Week 43: 497,000 ranged / 467,700 in stock).

**Why week, not day × store × category:** the spec's "executive model = day × store × category" is sized for a daily POS feed; the twelve cards, the three switchers (Week / Period to date / Year to date, as-of Sunday 25 Oct) *(superseded 2026-10-29 by the granularity picker of (k); still week-aligned — every item is a set of whole retail weeks)*, the three comparators (Budget / LY same week / Last week) *(Last week → Previous item, (k))* and every drill step in v5 down to "store × category × week" are week-aligned. Day grain would multiply the sales fact by 7 (≈ 0.9 M rows) and the generator's complexity (daily seasonality, trading-day flags) for a figure no card shows. `dim_date` keeps the day calendar so a day-grain sales fact can be added later without touching the week keys.

**Alternative:** day × store × category for `fact_sales_week` → `fact_sales_day` (the caller's framing and the spec's wording). Pick it if the USER wants a **mid-week as-of** (WTD on a Wednesday) or the bench tile "Sales pace vs budget %" on the landing page. Reversal cost low: the week fact is then a build-time roll-up of the day fact; everything downstream keys on `week_key` either way. (Open question 3.)

### (e) 4-5-4 retail calendar: FY = 52 weeks Mon–Sun starting on the Monday of the week that contains 1 January

**Default:** FY2026 = Mon 29 Dec 2025 – Sun 27 Dec 2026; quarters of 13 weeks in 4-5-4 periods; **Period 10 = W40–W43 = 28 Sep – 25 Oct 2026; Week 43 = 19–25 Oct 2026 = P10 week 4 of 4** — exactly the v5 header, status line and period switcher strings. FY2025 = Mon 30 Dec 2024 – Sun 28 Dec 2025, so the LY key of FY2026 W43 is FY2025 W43 = 20–26 Oct 2025. **Every LY comparison joins on `ly_week_key`, never on dates** (spec: "LY comparisons by week key"); the dataset contains no 53-week year (both years are 52 weeks under this rule); the 53-week restatement rule is documented in the generator README but has no data to act on. Data span: FY2025 W1 … FY2026 W43 = 95 actual weeks; Budget covers FY2026 W1–W52. Season for Sell-through: `AW26` = FY2026 W32–W51 (20 weeks; Week 43 = season week 12 of 20, as in v5).

**Why this and not the v1 default ("FY starts on the Monday nearest 1 Feb"):** under a February start, 19–25 Oct 2026 is **week 38 (P9 week 3)**, not Week 43, and Period 10 would be November. The only calendar consistent with *all* the v5 strings (Week 43 = 19–25 Oct, Period 10 = 28 Sep–25 Oct, "week 4 of 4") is the January-anchored one above. The v5 **YTD label "FY2026 to date · 2 Feb–25 Oct 2026"** and the v1 default are the inconsistent parts; fixing them is one string in the prototype and the YTD window becomes 29 Dec 2025 – 25 Oct 2026 (43 weeks). (Open question 2 — flagged, not edited: the prototype is the USER's approved artefact.) *Superseded 2026-10-29 by (k): there is no YTD switcher any more; the same window is the Year item "FY2026 to date · 29 Dec 2025–25 Oct 2026" (E-92, E-98).*

**Alternative:** keep the February start and renumber the frame to "Week 38 · Period 9" — touches the title, status line, period switcher, every ⓘ example that says "week 43" and the v1 story. Rejected unless the USER prefers NRF numbering.

### (f) Control totals and the Week-43 story are the contract; both flavours reconcile to them

**Default:** `checks/control_totals_eur.csv` with columns `scope` (ALL, NL, BE, ONLINE — the four values of the region / format switcher), `period_key` (every actual week `W-FY2026-31 … 43` for the bars; `P-FY2026-10`; `YTD-FY2026`; and their LY and LW keys) *(the generator wrote `PTD-` / `YTD-FY2026-43` keys instead, README open point 8; superseded 2026-10-29 by the item keys of (k): `W-` · `P-` · `Q-` · `FY-` + `@k` like-length windows, E-99)*, `metric_code`, `value`. Metrics = every card value, every card input quoted in a v5 ⓘ worked example (gross sales, markdown value, returns, COGS, front margin €, back margin €, on-hand cost, on-order cost, forecast weekly COGS, ranged / in-stock SKU-days, season opening units + receipts + units sold, R52W front margin + average on-hand cost, PO lines due / OTIF, OpEx by cost type, LFL store count, LFL sales current / LY, channel net sales), every Budget value, the status code of each card, the 7 / 3 / 2 counts and the overall-dot colour under each candidate rule (see (i)). `verify.py` recomputes all of them from the written CSVs and asserts the Week-43 ALL row against the v5 table at display precision.

**Binding story values (Week 43, ALL, vs Budget):** Net sales €61.4 m (−€1.5 m / −2.4 %, Watch) · Total margin 36.3 % (+0.1 pp vs 36.2 %, On track, **prov.**) · Weeks of cover 11.4 (+1.9 vs 9.5, Watch) · Markdown 9.8 % of gross (+1.3 pp vs 8.5 %, Off track) · Availability 94.1 % (−2.9 pp vs 97 %, Off track) · EBITDA flash P10 €15.3 m (−€0.8 m / −5.0 % vs €16.1 m, Watch, **prov.**) · LFL +3.4 % (+0.4 pp vs 3.0 %, On track; 131 of 142 LFL stores) · Front GM 30.1 % (+0.1 pp vs 30.0 %, On track) · Sell-through 63.1 % (+1.1 pp vs 62 %, On track) · GMROI 2.7× (+0.2× vs 2.5×, On track) · OTIF 95.4 % (+0.4 pp vs 95 %, On track) · Channel mix 68.4 / 19.9 / 11.7 (plan 70.0 / 18.0 / 12.0; online +1.9 pp, On track). The 12 prior weeks (W31–W42) follow the v5 `pts` series in shape; their exact values are whatever the generator writes (the control totals, not the prototype, are the truth for the bars).

**Why:** the P&L and Mirelo both proved that a flavour is "done" only when it reproduces the checks file; Nordmark gets the same gate from day one (ADR-0011 §3 parity gate). Putting the inputs of the ⓘ examples into the checks file keeps the pop-up copy honest in both flavours.

### (g) PBI flavour = its own PBIP in `pbi-report/Nordmark Exec/`

**Default:** `pbi-report/Nordmark Exec/Nordmark Exec.pbip` with `Nordmark Exec.SemanticModel` (TMDL, Import from `DataFolder`, compatibility level as Mirelo) and `Nordmark Exec.Report` (PBIR, one page `exec_landing` **1440 × 810**, the v5 fold; bookmark pop-ups for How to read / Notes / More KPIs; a hidden tooltip page for the card ⓘ as in Mirelo's `tt_card_info`; the Filters menu as a bookmark state of the side bar), `tests/control-totals.dax` (T-N1 … against `checks/control_totals_eur.csv`), `README.md`. Header pickers as disconnected parameter tables (`param_period`, `param_comparator`, `param_region`), window measures turning them into a `week_key` range — the Mirelo / P&L engine pattern. Status, Δ and the dot through dispatcher measures keyed on `dim_kpi` (`KPI Actual / Target / Δ / Δ % / Status`), as the spec's "Dispatcher measures" row asks, so cards, the drawer and the status line bind to one set. Accepted platform differences, to be added to `docs/design/parity-rules.md` as for Mirelo: solid pop-up panels instead of frosted glass (ADR-0012 §2.5), no CSS pulse on the dot (static dot; colour and tooltip identical), `FitToPage` instead of the responsive breakpoints, Segoe UI instead of Inter, bars as SVG image measures (card visual limits — measure the N-01-style budget on the first build, the v1 risk 3).

**Alternatives:** (1) a page inside the Mirelo or P&L PBIP — different model, design system, refresh and tests; rejected (ADR-0011 (b) reasoning). (2) 1920 × 1080 canvas per the spec — v5 is designed and fold-checked at 1440 × 810, the vosk.dev board size; rejected.

### (h) JS flavour = a standalone Next.js app in a new top-level folder — decided (USER 2026-10-28); proposed name `js-exec/`

**Decision:** the JS flavour is **not** a route inside `js-report/` (the ADR-0011 (c) choice for Mirelo). It is its own Next.js 16 app at the repo root, with its own `package.json`, lockfile, ESLint / Prettier / Vitest config, `next.config.ts` (the ADR-0002 §2.6 headers), build-data script and `public/data/` output. The USER chose standalone apps per report for the `.sync/` hand-offs: the pack is the folder itself (`npm ci && npm run build`), nothing to vendor out of another app, no shared bundle, no design-system leakage, no risk to the P&L route's LCP.

**Proposed folder name: `js-exec/`** (default) — follows the repo's `<platform>-<artefact>` pattern (`fabric-app/`, `pbi-report/`, `js-report/`, `fabric-data/`), pairs with the PBIP folder `pbi-report/Nordmark Exec/`, and leaves room for one `js-<report>/` per future showcase. **Alternative: `nordmark-app/`** — names the company instead of the artefact; clearer on a directory listing, but breaks the prefix pattern and would call for renaming on any re-brand. (Open question 4 — pick one; everything below assumes `js-exec/`.)

### (i) Overall-status pulse-dot rule = the literal v5 rule — decided (USER 2026-10-28)

- **Risks:** (1) the calendar — one wrong week key and every LY / LFL figure is quietly wrong; `verify.py` asserts `ly_week_key` by date arithmetic and the parity rows include an LY selection. (2) Power BI card limits — SVG bars, washes, borders and the dot are image measures; measure the page's query time on the first build and record it. (3) Naming collision "Track A / B / C" across the P&L and the new showcases (open question 1). (4) The prototype's switchers are label-only; the build makes them real — period / comparator / region change the numbers, so the generator must carry LY and LW values and the parity rows must cover a non-default selection. (5) Grain reversal (day vs week) is cheap now and expensive after the PBI model is built — answer open question 3 before phase 1. (6) Parallel builds drift on copy and names — the two sync points in (j) are mandatory, not optional. (7) Two Next.js apps in one repo: dependency versions must stay pinned identically (`js-report/`, `js-exec/`) or the hand-off README must say why they differ.
