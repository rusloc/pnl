# ADR-0014 — Hand-off packs in `.sync/`: one self-contained folder per report

- **Status:** **Accepted** (USER decisions 2026-10-28). **Amended 2026-10-30 (USER):** C1 — Power BI packs ship **with the loaded data** (model cache `.pbi/cache.abf` refreshed from the pack's own Parquet; `DataFolder` stays a placeholder); C2 — **publishing and embedding are done by another agent** from the USER's Power BI account and vosk.dev, never from this repo (pack READMEs and the hand-off note: publish the loaded model, no scheduled refresh, no IDs in `.sync`); C4 — **Mirelo ships as is** with its README caveats; **Nordmark joins** as `.sync/nordmark-exec/{js-app,power-bi,data}/`. See §2 items 7–9 and §3. **Amended again 2026-10-30, later the same day (USER):** item 7 (C1) is **superseded by item 10** — model caches and generated data in `.sync/` are **not kept in git**; `.sync/data-gen/` ships the generators + per-report READMEs and the receiving agent generates, refreshes in Desktop, checks and publishes. See §2 item 10, §3 and §4.
- **Date:** 2026-10-28
- **Decider:** USER
- **Applies to:** the ACME P&L report (Tracks B and C), the Mirelo Sales & Revenue report (Power BI + JS) and, later, the Nordmark executive dashboard (ADR-0013).
- **Amends:** ADR-0002 (Track C single app) and ADR-0011 (c) (`/sales` as a route in `js-report/`) **for the hand-off copies only**. Inside this repo `js-report/` stays one app with two routes, and `pbi-report/ACME Unified PnL` stays bound to `lh_raw` (Track A reads the published model).

## 1. Context

The USER publishes and hosts the Power BI and JS reports from another repo (vosk.dev). Until 2026-10-27 the hand-off was a set of dated notes plus a data copy (`.sync/track-c/data/`), and the other repo had to vendor files from `js-report/`. Three problems:
- `js-report/` holds two reports that share 4 small files; the build (`prebuild`) reads `../data/**`, so it fails outside this repo.
- The P&L Power BI model loads from the `lh_raw` SQL endpoint in the dev workspace RAW. That binding cannot go into `.sync/` (no endpoint / workspace IDs) and the publish target may not reach RAW.
- The Mirelo Power BI model reads local Parquet through an absolute `DataFolder` path.

## 2. Decision

1. **One folder per report** in `.sync/`: `.sync/pnl/` and `.sync/mirelo-sales/` (and `.sync/nordmark-exec/` later). Each holds `power-bi/`, `js-app/` and, where the data is not inside a flavour, `data/`. Each sub-folder has a README with the `.sync` header (from · to · date · status).
2. **JS flavour = a standalone Next.js app per report** (option (a) of nerd's assessment 2026-10-28). Shared code (glass, chart-scale, parquet-columns, csv) is **vendored** with a header naming its source of truth in `js-report/`. Prebuilt `public/data` ships committed; no `prebuild`; control-totals CSVs ship as test fixtures. Each pack must pass typecheck, lint, test and build on its own.
3. **Power BI flavour reads local Parquet** through a `DataFolder` text parameter with a placeholder value. The P&L pack gets its Parquet from the same type spec and derivations as `fabric-data/lh_raw/load_acme_pl.py` (ADR-0008 pre-translated columns + `fact_pl_elim`), so the pack and the lakehouse cannot diverge.
4. **Data:** Mirelo ships Parquet + the deterministic generator (seed 20261026) + control totals, not the CSVs (reproducible). Raw P&L CSVs are not shipped; the Parquet in the Power BI pack and the prebuilt JS data are enough to rebuild both reports. *(2026-10-30, item 10: the Parquet itself is no longer committed — the generator and control totals are; the pack folder is regenerated locally.)*
5. **AI chat is deferred** (USER 2026-10-28): no chat code in any pack; the chat notes in `.sync/` are marked deferred.
6. **Source of truth stays here.** A pack is a copy. Any change is made in `js-report/` / `pbi-report/` first and re-packed; pack READMEs say so. Older `.sync/track-c/*` artefacts are superseded by the packs but kept.
7. ~~**Power BI packs ship with the loaded data (C1, USER 2026-10-30).**~~ **Superseded by item 10 on 2026-10-30 (same day, later USER decision); kept for the reasoning trail.** Each PBI pack (P&L, Mirelo, Nordmark) carries its model cache `<name>.SemanticModel/.pbi/cache.abf`, refreshed from the pack's own Parquet, so the report opens with numbers and needs no refresh. `DataFolder` stays a placeholder: a refresh still needs it set to the pack's `data/` folder. The root `.gitignore` carries the exception `!.sync/**/.pbi/cache.abf` (added 2026-10-30); the repo PBIPs under `pbi-report/` keep their caches ignored. Binary size ≈ 14–25 MB per report. **Re-pack = refresh again** (the cache is part of the copy, so a stale cache is a stale pack).
8. **Publishing and embedding happen outside this repo (C2).** The USER hands the packs to another agent, who publishes the Power BI reports to the USER's Power BI account and embeds them (and the JS apps) on vosk.dev. This repo never publishes. Every pack README and the hand-off note must state: (a) **publish the already loaded model** — no refresh on upload *(2026-10-30, item 10: "loaded" now means loaded by the receiving agent's own Desktop refresh from the generated data — see item 10 step 3)*; (b) **no scheduled refresh** — the source is local Parquet, which would need a gateway; (c) **no IDs in `.sync`** — no workspace, dataset, tenant or capacity IDs, keys or connection strings (CLAUDE.md › Cross-repo sync folder).
9. **Mirelo ships as is (C4)** with the caveats in its pack README; **Nordmark joins** the packs as `.sync/nordmark-exec/{js-app,power-bi,data}/` (ADR-0013 (b), E-86), on the same rules — ~~the Nordmark PBI pack includes its cache (item 7), its `data/` holds the generated Parquet~~ *(2026-10-30, item 10: no cache and no committed Parquet; its `data/` is produced from `.sync/data-gen/`)*, and it is issued after the category filter lands (ADR-0013 (l); plan B8, so the pack is issued once).
10. **Model caches and generated data stay out of git; `.sync/data-gen/` ships the generators (USER 2026-10-30, later the same day — supersedes item 7).**
   - **Not in git:** every `<name>.SemanticModel/.pbi/cache.abf` under `.sync/` and the generated data outputs (Parquet / CSV) in the pack `data/` folders. They are gitignored; the `!.sync/**/.pbi/cache.abf` exception of item 7 is withdrawn. Copies already committed are removed from the index only (`git rm --cached`); **history is left as is — no rewrite.**
   - **Shipped instead:** one folder **`.sync/data-gen/`** holding the deterministic generator scripts and a README per report (P&L, Mirelo Sales, Nordmark Exec) on how to produce each pack's data. The receiving agent runs them.
   - **Receiving-agent sequence per Power BI pack:** (1) generate the data; (2) set `DataFolder` to the generated folder; (3) refresh in Power BI Desktop; (4) check against the committed control totals; (5) publish to the USER's Power BI account. Publishing / embedding remain with the USER's other agent (item 8), still **no scheduled refresh** (item 8 (b)) and **no IDs in `.sync`** (item 8 (c)).
   - **Stays committed:** the JS app packs' small prebuilt `public/data/` (they build without a generate step — item 2 unchanged) and the control-totals CSVs (small; the tests need them). ginee is confirming the final committed file list.
   - **Why:** repo size — the P&L cache alone is 61 MB (over GitHub's 50 MB warning) and every re-pack would add another full copy of three caches plus the Parquet to history; the data is fully reproducible from deterministic, seeded generators, so the copy carries no information the generator does not. Reversal cost of item 7 was low: nothing downstream depended on the committed binaries yet.

## 3. Consequences

- The other repo can take one report without the other, and build each without this repo's `data/`.
- Duplication: vendored files and Parquet copies add ~50 MB to the repo history; re-packing is manual until a pack script exists (idea: copy-list script + staleness test, like `chat-tools.json`).
- Two JS deploys and two CSP configs in the other repo.
- The packs ship before the USER's Desktop first-open check of both PBIPs; that check remains open.
- *(2026-10-30, superseded the same day by item 10 — see below)* ~~Three binary caches (≈ 14–25 MB each, ≈ 50–75 MB together) enter the repo history and grow it on every re-pack; accepted for a report that must open with numbers in another account.~~ Measured sizes were 25.5 / 61.2 / 25.4 MB (Nordmark / P&L / Mirelo). Still true: the caches are build output, not source — a pack whose cache predates its Parquet is wrong even if every file is present.
- *(2026-10-30, later, item 10)* The one-time copies already in history (three caches + the pack Parquet, ≈ 110 MB of binaries) stay there — no rewrite — but the history stops growing on re-pack: a re-pack now changes generator scripts, READMEs and control totals only. The cost moves to the receiving agent: a Power BI pack no longer opens with numbers; it needs the generate → `DataFolder` → Desktop refresh → check → publish sequence (item 10), so the `data-gen` READMEs are part of the contract and a missing step there becomes a question in the other repo. Byte-identical regeneration (deterministic seeds) is what makes the committed control totals a valid check against freshly generated data; ginee's regen check guards it.
- *(2026-10-30, later, item 10)* The repo PBIPs under `pbi-report/` are unaffected (their caches were always ignored); `.sync/` packs and `pbi-report/` sources now share the same rule — no model cache in git anywhere.
- *(2026-10-30)* Because another agent publishes, the packs are the complete contract: anything missing from a README (the loaded-model publish, the no-refresh rule, the `DataFolder` placeholder, the 1440 × 810 embed size, env-var names without values) becomes a question in the other repo. No scheduled refresh means the published reports are snapshots; a data change here is a re-pack and a re-publish there.
- *(2026-10-30)* Nordmark adds a third pack and a third JS deploy / CSP config in the other repo; the Mirelo caveats ship unresolved and are the other agent's input, not a blocker.

## 4. Notes

- *(2026-10-30)* **Placeholder reset without losing the loaded data (kept from the item 7 work; still useful whenever a model must be saved with a placeholder `DataFolder`).** Editing `DataFolder` in the TMDL *after* a Desktop save empties every imported table on the next open — the model re-evaluates the parameter against a path that does not exist. What works: refresh with the real path, then set the parameter to the placeholder **in the open model** (TOM, no refresh), then save in Desktop; the cache keeps its rows. Confirmed by bip on all three packs (Nordmark 26 tables / 878,120 rows, P&L 44 / 1,251,954, Mirelo 28 / 1,030,587). This is the second sighting of the "TMDL edit after save drops the Import cache" shape tracked as **CAND-029** (first: `///` description edits, daily 2026-10-29); promotion to `docs/ADD/anti-patterns.md` is bip's call, not done here.
